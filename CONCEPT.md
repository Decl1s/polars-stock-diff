# Какую задачу я решаю

Я моделирую запрос аналитика склада: после новой полной выгрузки объяснить,
какие пары warehouse/sku появились, исчезли или изменили физический остаток/резерв.
Я сравниваю два явно выбранных снимка, не веду скрытый baseline и не меняю WMS.
Это самостоятельный дополнительный учебный проект 27.10.2026, версия 0.1.0.

Я выбрал Polars для составного full join, выражений, группировки и Parquet.
Предыдущий проект серии был на Dagster; здесь я изучаю табличное сравнение.
Обычный dict по составному ключу был бы достаточен для нескольких строк, но хуже
показывал бы типы колонок, null semantics и дальнейший аналитический формат.

Входной договор: UTF-8 CSV с четырьмя колонками warehouse,sku,on_hand,reserved;
точный JSON manifest schema_version=1, snapshot_id,as_of,warehouses,complete,
row_count,csv_sha256. Complete должен быть true у обоих снимков, scope совпадать,
as_of нового строго больше старого, IDs различаться. Ключ уникален внутри снимка.
Reserved не превышает on_hand. Available вычисляю, а не доверяю отдельной колонке.

Я сохраняю только изменённые строки и summary со всеми четырьмя категориями.
Пустые полные снимки допустимы; все объявленные склады остаются в сводке с нулями.
Отчёт детерминирован в закреплённой проверенной среде и сортируется по ключу.
Manifest связывает файлы hash, что обнаруживает случайную порчу и перепутанные входы.
Подлинность и реальную полноту источника hash не доказывает.

Готовность я определяю поведением: четыре ожидаемые строки примера, сверка сумм,
отказ при partial/duplicate/плохой схеме, отсутствие незавершённого output,
повтор готового результата, Parquet round-trip и удобная CLI демонстрация.
Результаты ОС/CI/release фиксирую отдельно после их фактического выполнения.
Следующий возможный шаг — измеренный benchmark и обработка большого каталога
снимков; расписание, GUI, события Kafka и применение дельты в WMS пока не реализованы.
